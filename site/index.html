See what an AI agent could lift from your app. Close it in one command.

Tools such as rea let a coding agent read a shipped app without its source, explain how it works and rebuild it. Reaproof finds what makes that easy, such as a source map with your original code, a server key in the bundle or a .git folder in the output. It rates the risk in plain words and takes out what is safe to take out.

$ npx reaproof

It reads first and asks before it changes anything. Nothing to install, nothing to configure.

How it works

It reads, rates and explains. Then it asks.

  1. 1

    Run it where you build

    In a JavaScript project it finds the build output by name: dist, .next/static, out, build. Anything else, a folder, an app, a program or an archive, it reads as given.

  2. 2

    Read the rating

    The report opens with the rea risk, then every finding, worst first, with what it exposes and how to close it. It also says what it did not read.

  3. 3

    Say yes to the fix it can make

    It lists the source maps it can take out and, after a y, moves them to a backup outside your project. npx reaproof undo puts them back.

  4. 4

    Close the rest, run it again

    Each finding names the setting to change. A finding that is gone is fixed. The report ends with what to do next.

Every report opens with one of these

  • [very high]

    A tool like rea can take your original source or your secret values as they are.

    A source map that holds your source; a .env file, a .git folder or a server-only key in what ships.

  • [high]

    Near-secret values, data, or the inside of the running app are exposed.

    A database file or debug symbols in the output; a test key; a program signed with get-task-allow.

  • [moderate]

    Something left in makes the code easier to read, or the running app easier to get into.

    Code that is not minified; source maps that list file names; a program that kept its development names.

  • [baseline]

    None of the leaks this tool looks for was found.

    Code structure, the text in it and server addresses are still readable, as in any shipped app.

  • [not rated]

    What ships could not be read, so no rating is given.

    A disk image, an installer or an archive it does not open. It does not mean nothing leaks.

There is no "safe" level, because there is no such state. Screen structure and the server addresses an app calls stay readable in any app.

What it checks

The leaks that make an app easy to copy

CriticalFixed for you

Source maps that carry your code

A map with your original files hands them to anyone who downloads it. reaproof fix takes standalone maps out of the output and keeps a backup outside the project; undo puts them back.

CriticalHigh

Server keys and .env values

60 key patterns, looked for in code, scripts and settings files of any name, and in programs and bytecode for the services an app calls while it runs. Also any secret value from your own .env that appears word for word in what ships. Keys meant for browsers are not reported, and secrets are never printed in full.

CriticalHighMedium

Files that should never ship

A .env file, a .git folder, key stores, database files, debug symbols (.dSYM, .pdb, R8's mapping.txt) and the .DS_Store files the Finder writes.

MediumNote

Programs that keep their names

Function and variable names, debug information and build paths left in macOS and iOS (Mach-O), Linux and Android (ELF), Windows (PE) and WebAssembly. Notes say what stays in Go, Rust, .NET and Hermes code.

HighMedium

Release builds left in development mode

An Android app that is debuggable, test-only or signed with the debug key; a Mac program signed with get-task-allow or without the Hardened Runtime; Electron fuses left on, and the check of app.asar left off.

CriticalYour site

What your live site still serves

npx reaproof https://your-site checks whether the deployed site serves its source maps, for when a hosting platform builds from the repository and a local fix does not reach it.

Also: code that is not minified, source and test files packed in, long AI prompts in client code (a guess), and every server address your code names. Want rea's own view? reaproof measure runs the real rea on your output and counts what it reads, after asking. Every finding, with its severity and fix

Ways to use it

Yourself, with your agent, or in CI

Before you ship

npx reaproof

Run it in your project folder. If nothing is built yet, it offers to run your build first. The first time, npx asks Ok to proceed? (y): answer y.

With your AI agent

Run npx reaproof --json and fix what it reports.

Say that to any coding agent that runs commands. To make it reach for Reaproof by itself, install the skill once, for Claude Code, Codex, Cursor, Gemini CLI and other agents:

npx skills add Junhan2/reaproof

In CI, to stop a release

npx reaproof --fail-on high

It exits with 1 when something critical or high would ship. Add it after your build step. With --sarif the findings go to GitHub code scanning.

After you deploy

npx reaproof https://your-site.example

A local fix does not reach a site that a hosting platform builds from the repository. This checks what the live site serves. Use it on sites you run.

What you can point it at

Web, desktop, mobile, programs and the archives they ship in

Web builds

Next.js, Vite, Create React App, Nuxt and any folder of HTML, JavaScript, CSS and maps.

Desktop apps

Electron apps and their .asar, Tauri apps (their screen code is checked in the project folder), and Mac apps with every framework and helper inside.

Mobile apps

Android .apk and .aab, React Native bundles and Hermes bytecode, iOS .ipa, Flutter builds.

Programs

Mach-O, ELF and PE programs, .NET assemblies, Go and Rust builds, and WebAssembly modules. Read without running them.

Archives

.zip and every file in that format, such as .jar and .msix; .tar and .tgz as npm pack writes them. Three deep, in memory.

Not opened yet: .dmg, .pkg, .7z, .rar, .tar.xz and .tar.zst. The report lists them as unread, never as clean.

Ready for CI and review

Made to sit in a release pipeline

  • Exit codes that mean one thing each, so a release check never takes "could not read" for a pass.
  • --fail-on critical|high|medium sets the mildest finding that fails the step.
  • --json for agents and scripts: the verdict comes first, and text copied from scanned files is marked as data, not instructions.
  • --sarif for GitHub code scanning: one rule for each kind of finding, one result for each finding.
  • .reaproofignore for files you know about, in .gitignore patterns. The report names everything it left out.
  • Reads only by default. fix shows the list and asks, keeps a backup outside the project, and undo reverses it.
  • No dependencies. MIT. Node.js 18.3 or later on Linux, macOS and Windows.
Exit codes
0No leak at the --fail-on level or above (high, unless you set it)
1A leak at that level or above would ship
2A usage error, or a target that could not be settled on
3What ships could not be read: not rated
4Reaproof itself ran into an error

Get started

Your first check, in four steps

  1. Install Node.js 18.3 or later, if you do not have it.
  2. Build your app as you would for a release.
  3. In the project folder, run npx reaproof.
  4. Answer y to take out what it can, then fix the rest from the top and run it again.

Give it to your AI agent

npx skills add Junhan2/reaproof

In Claude Code you can also install it as a plugin:

/plugin install reaproof --marketplace Junhan2/reaproof

What it cannot do

Reaproof does not make an app impossible to copy. Nothing can.

  • Screen structure and the server addresses your app calls stay readable, because they reach the user's device.
  • Minified code stays readable in structure, and its numbers and strings stay as they are.
  • The only logic nobody can read is logic that runs on your server.
